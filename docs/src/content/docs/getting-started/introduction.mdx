title: Introduction
description: Understand rebaze's current migration paths and their limits
---

rebaze reads supported CMake or Gradle project information and generates Bazel
files for review and build validation. It targets Bazel 9 and is in early development.

## Current migration paths

| Source | Current behavior |
|---|---|
| CMake | Parse supported source forms or read configured CMake File API data; generate with the native backend or optional bazelle integration |
| Gradle | Extract supported Groovy/Kotlin build forms and generate JVM targets with the native backend |
| Maven | Detect `pom.xml`; migration is not implemented |
| Makefile, Cargo | Report their presence in `analyze`; migration is not implemented |

These parsers do not execute the full semantics of CMake or Gradle. Projects with
custom build logic can need manual migration. Native CMake test generation and
some dependency-strategy behavior remain incomplete.

## Generated output

Native generation produces `MODULE.bazel`, `BUILD.bazel`, and `.bazelversion`.
Gradle can also produce subproject BUILD files. CMake adds `.bazelrc` and can add
third-party dependency helpers.

Starlark values use typed serialization. Syntax tests establish that values stay
data and generated files parse; they do not establish valid labels or successful
builds for every project, dependency, or platform.

## Validation and effects

A native dry run previews files without writing or build validation. Normal CMake
migration first configures/builds the original project. After writing files,
normal CMake and Gradle migration run `bazel build //...`. A failed build leaves
generated files for inspection, and a successful build does not run project tests.

Bazel supports caching and controlled build inputs. A generated project that uses
host system libraries still depends on the host; migration alone does not make
that project hermetic.
