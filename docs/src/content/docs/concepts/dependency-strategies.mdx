---
title: Dependency Strategies
description: How managed pkg-config dependencies select system, source, or BCR providers
---

Native CMake generation resolves managed pkg-config dependencies before probing the
host or writing Bazel files. The resulting plan supplies every alias, target,
module declaration, and extension import.

## Implemented strategies

| Value    | Provider                                          | Requirements and limits                                                  |
| -------- | ------------------------------------------------- | ------------------------------------------------------------------------ |
| `system` | Snapshot of installed pkg-config packages         | Default; paths and libraries remain host-dependent                       |
| `source` | Checksummed archive built with `rules_foreign_cc` | Complete source metadata, a compatible toolchain, and build-system tools |
| `bcr`    | Module from the embedded BCR catalog              | Review the catalog's mapping, version, and target compatibility          |

`conan`, `vcpkg`, `prebuilt`, `bazelle`, `custom`, and unknown spellings fail
planning. An unsupported spelling in an unused override also fails.
Source archives have pinned bytes; this does not make every foreign build or
mixed system/source dependency graph hermetic.

## Selection and precedence

For `pkg_check_modules(COMPRESSION REQUIRED zlib)`, the generated alias is
`//third_party:compression`. Strategy selection uses this order:

1. An override for the normalized CMake prefix, `compression`.
2. An override for the requested package or its source-catalog identity, `zlib`.
3. `strategy.default`.

Normalization lowercases the prefix and replaces hyphens with underscores. A
multi-package alias can aggregate several targets. Conflicting package overrides
require an explicit prefix override. Multiple aliases claiming the same synthetic
pkg-config link are rejected; conflicting requests with one normalized alias also
fail rather than silently dropping a request.

```toml
[strategy]
default = "system"

[strategy.overrides]
compression = "source"
```

Change `rebaze.toml` and regenerate to change strategies. The generated
`third_party/config.bzl` records resolved intent; editing it does not replan
imports or build rules.

## System observations

Core runs pkg-config during migration, including preview, only for requests the
plan selects as system dependencies. Generated extensions replay that observation;
they do not run pkg-config at Bazel build time. Source-only and BCR-only plans
need no host package observations.

System wrappers expose include roots, including roots outside the installation
prefix, propagate joined `-DNAME=value` definitions, and retain ordered linker
arguments. Paths, spaces, quotes, and dollar signs are escaped for Bazel's option
processing. Other compile flags remain recorded data and require manual review;
this is not complete pkg-config compiler-flag conformance. Missing packages or
prefixes produce explicit stub repositories and warnings. A stub is not proof
that a dependency is usable.

## Source dependencies

Only active source packages and their transitive closure produce archive imports
and foreign build targets. Transitives inherit `source` unless overridden. A
system override uses the catalog's `pkg_config_packages`, or the catalog key when
that list is absent. Version predicates on transitive edges are preserved; compatible requests for
one system identity are combined, and ambiguous rebinding fails.

Missing metadata, ambiguous source identities, cycles, unsafe paths, invalid
checksums, and missing library outputs fail planning. See
[Build from Source](/rebaze/guides/source-builds/) for the metadata contract.

## BCR fallback and overrides

```toml
[strategy]
default = "bcr"
bcr_fallback = "system" # system or source

[strategy.bcr.version_pins]
zlib = "1.3.1.bcr.5"
```

Unresolved or skipped BCR packages use the configured fallback. Imports are
deduplicated by module while each package retains its target. Module overrides
rebind the repository and preserve the original package/target layout; the
replacement module must actually provide those targets. Pins apply to the final
module name. Conflicting module versions or apparent repository names fail.

Source/BCR version predicates support `=`, `<`, `<=`, `>`, and `>=` with numeric
dotted versions. Component count is significant: `1.2` is less than `1.2.0`.
BCR packaging suffixes of the form `.bcr.N` are excluded from this comparison.
Unsupported predicates fail explicitly. System requests retain their original
expressions for pkg-config to evaluate.

## Scope

The plan manages pkg-config requests and source transitives. Other explicit CMake
imported-target mappings retain their existing behavior and can require manual
module declarations. The extractor also attaches managed aliases conservatively
to generated libraries and executables; it does not reconstruct complete CMake
per-target dependency semantics. Review a generated project and build it before
relying on its compatibility.
