---
title: Generated Files
description: Native migration output, dependency plans, and overwrite behavior
---

Native generators return a complete path-to-content map before writing it.
Inspect this map with `--dry-run` and preserve your original project before a
writing migration.

## Project files

| File            | Content                                                          |
| --------------- | ---------------------------------------------------------------- |
| `MODULE.bazel`  | Project module, rule dependencies, and active dependency imports |
| `BUILD.bazel`   | Generated libraries/executables, or Gradle root targets          |
| `.bazelversion` | Bazel `9.0.0`                                                    |
| `.bazelrc`      | Native CMake language/compiler settings and review comments      |

The default CMake rules are `cc_library` and `cc_binary`, loaded from
`rules_cc` version `0.2.27`. Detected framework imports and explicitly configured
custom rules depend on the project. Gradle subprojects also receive their own
`BUILD.bazel` files.

## Managed CMake dependencies

CMake projects with pkg-config requests receive four additional files:

| File                          | Content                                                        |
| ----------------------------- | -------------------------------------------------------------- |
| `third_party/BUILD.bazel`     | Direct aliases or aggregate libraries plus active source rules |
| `third_party/config.bzl`      | Serialized resolved plan for inspection                        |
| `third_party/source.bzl`      | Active archive table and source module extension               |
| `third_party/system_deps.bzl` | Selected host observations and system module extension         |

An example source alias is:

```python
alias(
    name = "compression",
    actual = "//third_party:zlib_source",
)
```

Inactive source rules and repository imports are omitted. Helper files may have
empty tables. To switch providers, edit `rebaze.toml` and regenerate; editing the
inspection table alone does not change aliases or imports. Read
[Dependency Strategies](/rebaze/concepts/dependency-strategies/) for precedence
and [Build from Source](/rebaze/guides/source-builds/) for metadata.

## Writing and recovery

Writing migration replaces existing generated files. Each file is staged and
replaced atomically after output-path preflight. The entire output set is not a
transaction: a later I/O failure can leave an updated subset. Build validation
failure also leaves files for inspection. Rerun from a preserved checkout or
restore it through version control before retrying.

Changing strategies can leave old helper files from an earlier migration on
disk; only active imports and targets in the new output are used. Keep manual
customizations in configuration or separate files where possible, and inspect
the generated diff before accepting it.
