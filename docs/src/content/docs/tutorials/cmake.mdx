Use rebaze's checked-in C fixture to compare an original CMake build with generated
Bazel targets. It contains two libraries, a public header, an executable and a
literal CTest registration in a child directory.

## Prerequisites

Install rebaze, Bazel 9, CMake/CTest, Make and a C compiler. Bazel may download its
pinned dependencies. See [Installation](/rebaze/getting-started/installation/).
Use a source checkout of the rebaze revision matching your binary for the fixture.

From that checkout, copy the input to a disposable directory:

```bash
cp -R crates/rebaze-cli/tests/fixtures/cmake /tmp/rebaze-cmake-example
```

Choose a fresh destination if it already exists. The fixture deliberately changes
a source variable after creating a target and changes a parent variable inside a
child directory. Both builds must preserve the original command order and scope.

## Build and test the original

```bash
cmake -S /tmp/rebaze-cmake-example -B /tmp/rebaze-cmake-original-build
cmake --build /tmp/rebaze-cmake-original-build
ctest --test-dir /tmp/rebaze-cmake-original-build --output-on-failure --no-tests=error
```

CTest should report one passing test. Missing source files or leaked variable
state will fail configuration or compilation.

## Preview and migrate

```bash
rebaze analyze /tmp/rebaze-cmake-example
rebaze migrate /tmp/rebaze-cmake-example --build-generator native --dry-run
```

Preview prints generated files without creating them or running builds. Inspect
`dep`, `scope`, `probe` and `ctest_value` in the proposed BUILD file. Then migrate:

```bash
rebaze migrate /tmp/rebaze-cmake-example --build-generator native
```

Normal migration validates the original and generated builds. It does not run
their test suites; run Bazel tests explicitly:

```bash
cd /tmp/rebaze-cmake-example
bazel test //... --test_output=errors
bazel run //:probe -- "two words'$" 42 ""
```

Expect `ctest_value` to pass and the executable to print `rebaze fixture: 42`.
The arguments intentionally exercise spaces, a quote, a dollar sign and an empty
argument. For the complete success/failure oracle, see the source checkout's
`CONTRIBUTING.md`.

## Unsupported source evaluation

Native source migration accepts a limited static profile. Ordinary `set` and
`list(APPEND/PREPEND ...)` changes are observed in order; child directories inherit
an isolated context at their call. Required child listfiles must exist.

Conditions, loops, function/macro bodies, custom includes, `find_package` calls,
cache/environment/parent-scope assignments, unmodeled list/variable forms and
cross-directory target mutation require evaluated evidence. The source parser
can analyze syntax without making those constructs safe to migrate. Unsupported
intent returns an error before generated files are replaced.

<Aside type="caution">
  A dependency mapping supplies a Bazel edge; it does not evaluate CMake modules
  or authorize ignoring their effects on source variables. Unknown required links
  fail rather than becoming skipped dependencies.
</Aside>

## Select configured File API evidence

For a project requiring CMake evaluation, explicitly create a codemodel query,
configure with the project's required options, then require that evidence:

```bash
mkdir -p build/.cmake/api/v1/query
touch build/.cmake/api/v1/query/codemodel-v2
cmake -S . -B build
rebaze migrate . --build-generator native --cmake-build-dir build --cmake-file-api-only
```

Run these commands from that project's root. Normal validation refreshes the build
before capturing replies. Preview and `--unsafe-mode` read existing replies without
refreshing them. `--cmake-file-api-only` prevents fallback to source extraction.

File API input is a separate path with incomplete compiler/usage semantics and no
test-registration import. Successful generation is not proof that all project
behavior migrated. Review outputs and independently build/test the generated
project before adopting it.
